# ADR-007: Raw JSON Payload Archiving for Point-in-Time Auditability

## Intent

FRED retroactively revises historical series values after publication (e.g.,
seasonal adjustment corrections). Re-running the pipeline over a past date
range today will produce slightly different numbers than a run performed on
the original date. Without preserving what the data looked like at decision
time, the system cannot defend a past OVERBUY recommendation to a CFO or
auditor. This ADR documents the decision to archive the full raw FRED JSON
response — including per-observation vintage metadata — at acquisition time.

## Decision

1. Create a dedicated `get_fred_series_with_payload()` function in
   `FRED_helper.py` that returns both the processed DataFrame and the
   complete raw JSON response from FRED.
2. In `acquire.py`, write the full JSON payload to a timestamped file
   (`{series_id}_{UTC_timestamp}.json`) immediately after each successful
   fetch — before any transformation occurs.
3. The archived payload must include FRED's `realtime_start` and
   `realtime_end` fields per observation, which identify the exact vintage
   of each data point.
4. Processed CSVs (`{series_id}.csv`) are retained for convenience but are
   not the authoritative audit record — the raw JSON archive is.

## Consequences

### Positive

- Point-in-time reconstruction is possible: given a past recommendation date,
  an engineer can load the corresponding archived JSON and reproduce the exact
  S_score that was computed on that day.
- Vintage metadata (`realtime_start`/`realtime_end`) makes FRED's revision
  history traceable at the observation level.
- Archiving happens before transformation — even if the pipeline fails
  mid-run, the raw inputs are already preserved.

### Negative

- Storage grows with every pipeline run — each run writes four timestamped
  JSON files with full historical observations.
- No automated retention policy; old archives must be manually pruned or
  the results directory grows indefinitely.
- Adds a second HTTP response parsing path (`get_fred_series_with_payload`
  alongside `get_fred_series`), increasing surface area in `FRED_helper.py`.

## Alternatives Considered

| Alternative | Pros | Cons | Why Not |
|------------|------|------|---------|
| Archive processed CSV only | Smaller storage footprint | Loses vintage metadata and raw values; cannot reconstruct original inputs after FRED revises them | Insufficient for point-in-time auditability |
| No archiving (in-memory only) | No storage overhead | Recommendations are undefendable after process exit; directly violates Auditability characteristic | Unacceptable for a high-stakes financial decision system |
| Store vintage data in a database audit table | Queryable; structured | Reintroduces database dependency rejected in ADR-003; adds schema management overhead | Inconsistent with file-based persistence decision |

## Requirements Checklist

1. [x] `get_fred_series_with_payload()` implemented in `FRED_helper.py`
2. [x] Raw JSON payload archived with UTC timestamp on every successful fetch
3. [x] Archived payload includes per-observation `realtime_start`/`realtime_end`
4. [x] Archiving occurs before transformation begins
5. [ ] Retention policy defined for old archive files
