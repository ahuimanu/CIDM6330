# ADR-006: Asymmetric PPI Weighting — Embedding Business Rule in Pipeline

## Intent

The S_score formula defined in Foundation 2 treats rising semiconductor prices
as a negative supply signal: `S = w1(ΔIP) + w2(ΔCapUtil) - w3(ΔPPI) + w4(ΔInv)`.
An early implementation applied equal positive weights to all four series,
which caused rising prices to be treated the same as rising production —
producing a less accurate and potentially misleading recommendation. This ADR
documents the decision to encode the negative PPI relationship directly into
the pipeline as a first-class architectural commitment.

## Decision

1. Apply asymmetric weights in `pipeline.py` as the production default:
   - `IPG3344S`: `+1.0` (rising production = good supply signal)
   - `CAPUTLG3344SQ`: `+1.0` (rising capacity utilization = good supply signal)
   - `A34STI`: `+1.0` (rising inventories = good supply signal)
   - `PCU334413334413`: `-1.0` (rising prices = bad supply signal)
2. Pass these weights via the existing `weights` parameter in
   `transform_combined()` — no changes to the transformation logic required.
3. Document the business rationale in code comments so future maintainers
   cannot accidentally revert to equal weights without understanding the impact.

## Consequences

### Positive

- S_score accurately reflects the domain model — a price spike now moves the
  score toward OVERBUY rather than masking it.
- Business rule is explicit and visible in `pipeline.py` rather than buried in
  documentation; a code reviewer can see and challenge it.
- Existing `weights` parameter in `transform_combined()` required no new
  engineering — the mechanism was already in place.

### Negative

- Weight values (`+1.0`, `-1.0`) are hardcoded in `pipeline.py`; changing the
  formula requires a code change, not a configuration change.
- Equal-weight behavior is no longer the default, which could surprise a
  developer adding a new series without reading the existing weight map.

## Alternatives Considered

| Alternative | Pros | Cons | Why Not |
|------------|------|------|---------|
| Equal positive weights for all series | Simpler; no domain knowledge required | Rising PPI improves S_score — directly contradicts the supply chain model | Produces mathematically incorrect recommendations in price-spike scenarios |
| Invert PPI interpretation at recommendation layer | Keeps transform logic neutral | Pushes domain logic downstream, making the S_score itself misleading as an intermediate value | S_score would be uninterpretable outside of the final threshold comparison |
| Configurable weights via external config file | Flexible for future tuning | Adds configuration management overhead for a single known business rule | Over-engineered for a stable, well-defined formula |

## Requirements Checklist

1. [x] `PCU334413334413` assigned weight `-1.0` in `pipeline.py`
2. [x] All other series assigned weight `+1.0`
3. [x] Weight map passed to `transform_combined()` on every pipeline run
4. [x] Code comment explains business rationale for the negative PPI weight
