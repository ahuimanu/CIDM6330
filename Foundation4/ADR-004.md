# ADR-004: Fail-fast Pipeline — Reliability vs. Data Integrity

## Intent

The Shortage Scout pipeline produces a high-stakes financial recommendation
(OVERBUY/HOLD) that could trigger a multi-million dollar inventory decision.
During implementation it became clear that a pipeline producing partial or
silent output is more dangerous than one that produces no output at all. This
ADR documents the decision to halt the entire pipeline on any filter failure
rather than continue with degraded data.

## Decision

1. Any unhandled exception in any pipeline filter (acquire, transform,
   calculate) terminates the entire run with a logged error.
2. The pipeline produces no output artifact if any filter fails — no partial
   `transformed.json`, no partial CSV.
3. The validation filter in `transform.py` raises a `ValueError` and halts
   execution if percent-change values fall outside `[-1.0, 1.0]`, rather
   than continuing with suspect data.
4. Missing series detected after acquisition abort the pipeline before
   transformation begins.

## Consequences

### Positive

- Eliminates the risk of a mathematically fraudulent S_score reaching a
  decision-maker — a loud failure is always preferable to a silent wrong answer.
- Simplifies debugging: a halted pipeline with a logged error is immediately
  visible; corrupt output is not.
- Consistent with the Data Integrity driving characteristic — the architecture
  was explicitly designed to prevent silent normalization failures.

### Negative

- The pipeline is less reliable by definition — any single failure produces
  zero output rather than best-effort output.
- A transient network failure fetching one of four series aborts the entire
  run, even if the other three series fetched successfully.
- Operations team must monitor for pipeline halts and manually re-trigger runs
  after failures are resolved.

## Alternatives Considered

| Alternative | Pros | Cons | Why Not |
|------------|------|------|---------|
| Best-effort output (skip failed series, score on remaining) | Pipeline always produces some output | S_score computed from 3/4 signals is silently less reliable; decision-maker has no indication the output is degraded | Silent degradation is the exact failure mode the architecture is designed to prevent |
| Retry indefinitely before failing | Reduces transient failure impact | Could hang the pipeline for an unbounded time; masks persistent failures | Retry with backoff already implemented; indefinite retry adds risk without bound |
| Warn and continue with NaN-filled gaps | Keeps pipeline running | NaN propagation into S_score produces undefined mathematical output | Mathematically invalid; violates Data Integrity |

## Requirements Checklist

1. [x] Pipeline logs a fatal error and exits on any unhandled filter exception
2. [x] Validation filter raises `ValueError` on out-of-range percent-change values
3. [x] Missing series detected and logged before transformation begins
4. [x] No partial output artifact written on pipeline failure
