# ADR-002: Architecture Style — Pipeline over Microservices

## Intent

The Shortage Scout system requires strict sequential mathematical
transformations to produce a valid S_score. The architecture style must
preserve the order of operations (normalize → smooth → calculate) and
guarantee that no step executes on un-validated inputs. This ADR documents
why a Pipeline architecture was chosen and why Microservices — the primary
alternative — was rejected.

## Decision

1. Adopt a Pipeline architecture as the single architecture style for
   Shortage Scout.
2. Structure the system as five sequential filters: Ingestion → Normalization
   → Aggregation → Calculation → Enrichment & Output.
3. Treat the entire pipeline as a single deployable artifact (one architecture
   quantum).
4. Enforce unidirectional data flow — no filter may read from or write to a
   filter downstream of it.

## Consequences

### Positive

- Sequential filter execution guarantees order of operations — the S_score
  calculation cannot run before normalization completes.
- Each filter can be unit-tested in isolation by injecting a static DataFrame,
  satisfying the Testability driving characteristic.
- A dedicated Validation Filter can be inserted at the transformation boundary
  to assert data integrity before the S_score calculation runs.
- Single deployable artifact reduces operational complexity — no service
  discovery, no network calls between components.

### Negative

- A failure in any single filter halts the entire pipeline with no partial
  output (this tradeoff is documented explicitly in ADR-004).
- The architecture cannot scale individual filters independently; if ingestion
  becomes a bottleneck, the whole pipeline must be scaled.
- Adding a new data source requires modifying the pipeline rather than
  deploying an independent service.

## Alternatives Considered

| Alternative | Pros | Cons | Why Not |
|------------|------|------|---------|
| Microservices | Independent deployability; each transformation scales independently | Network calls between sequential math steps introduce latency and data integrity risk; testing requires spinning up multiple services | Sequential math cannot tolerate network drops between normalization and calculation |
| Monolithic script (no filter separation) | Simplest to write | No testability; all logic coupled; impossible to insert validation boundaries | Violates Testability and Data Integrity driving characteristics |
| Event-driven / streaming (e.g., Kafka) | Real-time processing capability | Massive infrastructure overhead for a monthly batch job; no benefit for non-real-time use case | Over-engineered for monthly cadence |

## Requirements Checklist

1. [x] Five distinct filter components implemented with clear boundaries
2. [x] Each filter accepts and returns a DataFrame (enforced data contract)
3. [x] Validation filter present at the transformation boundary
4. [x] Pipeline executes as a single deployable Python artifact
5. [x] Unit tests exist for each filter in isolation without live API calls
