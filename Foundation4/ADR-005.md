# ADR-005: Strict NaN Handling as Default — Data Completeness over Availability

## Intent

FRED series have different publication cadences. Near month boundaries, one
or more series may not yet have published the latest month's value, producing
a row with partial NaN values after the outer join. This ADR documents the
decision to default to strict NaN handling — dropping any row where any series
is missing — rather than scoring months with incomplete data.

## Decision

1. Set `strict=True` as the default in `transform_combined()`, applying
   `dropna(how="any")` to enforce complete-row-only scoring.
2. Expose `strict=False` as an explicit opt-in for historical analysis or
   debugging where partial rows are acceptable.
3. Near month boundaries, the current month produces no recommendation rather
   than a recommendation based on incomplete inputs.

## Consequences

### Positive

- Guarantees every S_score is computed from all four series — no silent
  reduction in signal quality near month boundaries.
- Consistent with the Data Integrity driving characteristic and the fail-fast
  decision in ADR-004.
- Makes the pipeline's behavior near month-end predictable and auditable —
  "no output" is an unambiguous signal to wait for complete data.

### Negative

- Near month boundaries the pipeline produces no recommendation for the
  current month, which may be operationally inconvenient.
- Operators must know to re-run after all four series have published rather
  than treating a missing recommendation as a pipeline failure.

## Alternatives Considered

| Alternative | Pros | Cons | Why Not |
|------------|------|------|---------|
| Loose default (`strict=False`, original) | Pipeline always produces output for the current month | S_score silently computed from 3/4 signals; decision-maker unaware of degraded reliability | Silent degradation; inconsistent with Data Integrity characteristic |
| Always strict, no opt-out | Maximum integrity | No escape hatch for historical analysis or debugging scenarios | Unnecessarily rigid; opt-out has legitimate uses |
| Impute missing values (e.g., forward-fill) | Produces complete rows | Introduces synthetic data into a financial recommendation model | Fabricating inputs to a high-stakes model is unacceptable |

## Requirements Checklist

1. [x] `transform_combined()` defaults to `strict=True`
2. [x] `strict=False` available as explicit parameter for opt-in loose behavior
3. [x] Existing tests unaffected (all test DataFrames are fully populated)
4. [ ] Test added to assert strict mode drops incomplete trailing rows
