# ADR-003: File-based Output over a Database

## Intent

The pipeline must persist both raw inputs and transformed outputs in a way
that satisfies the Auditability driving characteristic — an engineer must be
able to reconstruct exactly what data and calculations produced a given
OVERBUY/HOLD recommendation on any past date. This ADR documents the decision
to use flat files (CSV and JSON) rather than a database as the persistence
layer.

## Decision

1. Write each fetched series to an individual CSV file (`{series_id}.csv`)
   per pipeline run.
2. Archive the full raw FRED JSON payload (including vintage metadata) to a
   timestamped file (`{series_id}_{timestamp}.json`) at acquisition time.
3. Write the final transformed output to `transformed.json` after each run.
4. Do not introduce a database (SQLite, PostgreSQL, or otherwise) for v1.

## Consequences

### Positive

- Timestamped raw JSON files on disk provide a natural, immutable audit trail
  — no additional versioning or audit-table engineering required.
- No database server to install, configure, or maintain; the pipeline remains
  a single portable artifact.
- Files are human-readable and inspectable without tooling, simplifying
  post-run debugging.
- Aligns with the monthly batch cadence — concurrent write support is not needed.

### Negative

- Querying historical recommendations requires reading and parsing multiple
  files rather than a SQL query.
- No referential integrity — nothing prevents a file from being manually
  deleted or overwritten, breaking the audit trail.
- Storage will grow unbounded over time as timestamped JSON archives accumulate.

## Alternatives Considered

| Alternative | Pros | Cons | Why Not |
|------------|------|------|---------|
| SQLite | Queryable; single file; no server | Requires extra engineering to store raw vintage payloads alongside processed rows; audit tables add schema complexity | Overhead unjustified for monthly batch job |
| PostgreSQL | Full ACID compliance; concurrent access | Requires a running server; significant setup cost for a batch job that runs once a month | Infrastructure cost far exceeds requirements |
| In-memory only (no persistence) | Simplest | No audit trail; recommendations unrecoverable after process exit | Directly violates Auditability driving characteristic |

## Requirements Checklist

1. [x] Raw FRED JSON payload archived with timestamp on every acquisition run
2. [x] Per-series CSV written to results directory each run
3. [x] Final transformed output written to `transformed.json`
4. [x] No database dependency in `requirements.txt`
